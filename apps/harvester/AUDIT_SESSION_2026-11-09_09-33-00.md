## Executive result

A process-restart persistence integration gap is confirmed in current `develop`: Harvester creates fresh in-memory trading projections and explicitly disables Journal replay. The shared Journal package has bounded read/replay capability, but Harvester startup does not invoke it or receive restored state.

The runtime consequences (missed offline fill accounting, duplicate new order, double accounting, or incorrect reservation decisions) are strongly indicated by the source paths but have not yet been reproduced in an end-to-end process-death/restart scenario. Do not describe them as confirmed incidents.

## What was inspected

### Startup composition and state ownership

- `apps/harvester/src/bootstrap/start-harvester.js` — initializes a fresh Portfolio, empty RecoveryLedger map, empty OrderRegistry and empty recovery/session collections; comment explicitly disables Journal replay.
- `apps/harvester/src/use-cases/create-portfolio-workflow.js` — creates Portfolio and RecoveryLedger projections in memory unless initial state is injected.
- `apps/harvester/src/domain/portfolio/portfolio.js`, `position.js`, and `src/domain/strategies/conservative/recovery-ledger.js` — position/accounting facts and fill IDs/fingerprints are owned by immutable in-memory objects.
- `apps/harvester/src/domain/orders/order-registry.js` — registry owns canonical orders; unknown exchange orders are deliberately not adopted.
- `apps/harvester/src/use-cases/conservative-trading-engine.js` — `reconcileOwnedOrders()` snapshots the existing registry; when it is empty, it returns `reconciled: 0` without querying canonical order or fill history.

### Journal and startup tests

- `packages/journal/README.md` — read/replay validates bounded complete history and invokes consumers sequentially; replay is at-least-once, not exactly-once.
- `apps/harvester/src/infrastructure/journal/prepare-optional-journal.js` — starts Journal and exposes ready/flush/close; no read/replay.
- `apps/harvester/src/index.js` — composes Journal and calls `startHarvester({ eventPublisher })`; no restored projection is passed.
- `apps/harvester/src/bootstrap/start-harvester.test.js`:
  - “starts from fresh in-memory state without replaying historical Journal records” injects malformed `journalRecoveryRecords`, instruments historical broker reads, asserts no history reads and `userDataReady === true`.
  - “journals pre-existing account-wide orders and allows trading startup without adopting or changing them” proves the unowned-order audit classification does not itself block runtime startup.
- These tests characterize current no-replay/unowned-order behavior. They are not crash/restart recovery tests.

### Graceful versus unexpected termination

- `apps/harvester/src/index.js` registers SIGINT and SIGTERM handlers.
- `apps/harvester/src/bootstrap/shutdown/create-shutdown-handler.js` performs owned-order reconciliation before and after the owned-BUY cancellation pass, keeps user-data intake active through final reconciliation, preserves open SELLs, and writes a durable CLOSING balance snapshot.
- The process closes Journal/EventBus and releases process locks only after confirmed shutdown.
- SIGKILL, process crash and power loss bypass signal handlers and cannot guarantee graceful CLOSING publication. Stale locks are not automatically reclaimed; the operator must verify process ownership before manual cleanup.

## Broker history capability and completeness

The current `@coinzilla/brokers` contract exposes canonical `getFills({ symbol, orderId?, fromId?, startTime?, endTime?, limit? })`. A symbol-wide query can therefore discover trades without a local order ID. This is a useful building block for recovery, but current Harvester does not invoke it at startup.

The official [Binance Spot WebSocket API myTrades documentation](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/account) specifies:

- `fromId` is inclusive (trade ID greater than or equal to the cursor).
- Maximum page size is 1,000.
- Time-filtered queries are limited to a 24-hour interval.
- `fromId` cannot be combined with `startTime`/`endTime`.
- `orderId` cannot be combined with time filters, but can be combined with `fromId`.
- Without a filter, the endpoint returns the most recent trades up to the requested limit.

The broker package validates cursor IDs and rejects values outside JavaScript's safe-integer range rather than rounding int64 trade IDs. The official documentation reviewed does not establish a guaranteed retention horizon. Thus a complete scan needs durable per-symbol cursors, strict pagination/page-exhaustion validation, market-universe coverage, exact identifier handling and an explicit policy for unavailable historical data. The existence of the API does not prove all offline executions are retrievable.

## Documentation discrepancy

`apps/harvester/docs/JOURNAL_OPERATIONS.md` stated that Harvester reads all prior Journal sessions and blocks trading startup when previous trading events exist. Current source composition does not implement that gate. The operational documentation is corrected in this documentation change.

## F-028 — applied-fill Journal durability boundary

A second confirmed source-level gap compounds F-011:

- The Conservative engine applies a fill to accounting, then publishes `FILL_APPLIED`; the fill path does not call `eventPublisher.flush()`.
- `makeEventPublisher.publish()` is synchronous admission only. EventBus subscriber handlers are scheduled asynchronously and tracked as pending.
- Journal `record()` appends through a write queue and returns `durable: false`; Journal `flush()` waits for EventBus delivery and queued writes, then calls filesystem sync/fsync.
- The engine's only `eventPublisher.flush()` is the pre-side-effect intent barrier. It protects order placement/cancellation, not the applied-fill event.
- Graceful close drains pending work and syncs Journal. Abrupt termination/power loss has no equivalent guarantee.

**Classification:** confirmed lack of an immediate durability guarantee; no actual lost-fill incident reproduced. A crash in the publication/subscriber/write/sync window may leave the next process without a durable fill fact, which compounds the lack of startup replay in F-011. Journal is operational evidence, not a complete crash-consistent state ledger.

Existing tests verify fill-event publication and pre-side-effect intent durability, but no inspected Harvester test asserts durable flush immediately after applied fill. Future DDD/TDD work must define a crash-consistent ordering for fill fact persistence, accounting projection advancement and checkpoint advancement, with failure injection at each boundary.
