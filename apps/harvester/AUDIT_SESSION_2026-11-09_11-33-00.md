It creates fresh Portfolio, RecoveryLedger, OrderRegistry, pause and recovery-intent state.

**Important correction:** the repository does retain a substantial, tested offline recovery helper pipeline introduced by PR #606. The helper code is not missing; current startup composition no longer invokes it.

The historical PR #606 startup integration was fail-closed for prior trading activity because it passed `marketUniverseComplete: false` into `auditRecoveredTradeHistory()`, which explicitly requires `true`. The 2026-11-05 roadmap decision deferred runtime integration for the first Conservative TESTNET workflow. Current runtime later bypassed that fail-closed recovery gate instead of solving historical market-universe completeness. It now starts fresh and can proceed with unowned open orders; this is not an equivalent safety guarantee.

The runtime consequences (missed offline fill accounting, duplicate new orders, double accounting, or incorrect reservation decisions) are strongly indicated by source paths but have not been reproduced in an end-to-end process-death/restart scenario. Do not describe them as confirmed incidents.

## Broker order identity recovery

- Durable `order.submission_requested` facts preserve `clientOrderId`.
- Broker `brokerOrderId` can be recorded by the submission acknowledgement, cancellation intent/failure, or applied-fill event.
- The engine's `reconcileOwnedOrders()` can also resolve a restored registry entry missing a broker ID through `broker.getCanonicalOrder({ symbol, clientOrderId })`, validate the returned symbol/client ID, and attach the canonical broker ID.
- Existing engine tests cover accepted orders after a lost submission acknowledgement, unresolved client-ID lookup, mismatched client IDs and immutable-intent conflicts.
- If the client-ID lookup cannot resolve the order, it remains UNKNOWN and reconciliation fails closed. The current runtime cannot use this path after restart because it does not restore the registry entry containing the client ID.

## Broker history capability and completeness

The current `@coinzilla/brokers` contract exposes canonical `getFills({ symbol, orderId?, fromId?, startTime?, endTime?, limit? })`. The offline `fetchAccountTradeHistory()` helper uses symbol-wide pagination for a supplied Market list, but current startup does not invoke it.

The official [Binance Spot WebSocket API myTrades documentation](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/account) specifies:

- `fromId` is inclusive.
- Maximum page size is 1,000.
- Time-filtered queries are limited to a 24-hour interval.
- `fromId` cannot be combined with `startTime`/`endTime`.
- `orderId` cannot be combined with time filters, but can be combined with `fromId`.
- Without a filter, the endpoint returns the most recent trades up to the requested limit.

The broker package rejects trade/fill cursor IDs outside JavaScript's safe-integer range rather than rounding int64 identifiers. The official documentation reviewed does not establish a guaranteed historical-retention horizon. The helper cannot prove complete account history while the full historical symbol universe is unknown.

## PREFLIGHT, user-data queue and trading readiness

- `subscribeToUserData()` starts the user-data stream, captures the PREFLIGHT account/open-order snapshot, durably flushes required audit events, drains queued user-data events and then sets `state.ready = true` if other safety flags remain clear.
- User-data events arriving after stream connection but before PREFLIGHT completion are queued and processed before readiness. An execution event for an unowned order can set accounting failure and keep readiness closed.
- Events that occurred while Harvester was offline before the new stream connected are not delivered by that stream. A terminal offline fill is absent from the current open-order snapshot; current startup does not scan trade history.
- The open-order audit's `BLOCKED` / `UNOWNED_OPEN_ORDERS` classification is not a trading-readiness gate. The existing test “journals pre-existing account-wide orders and allows trading startup without adopting or changing them” verifies market subscriptions/runtime startup with the order still unowned.
- That test's fake broker emits no market-price tick. Its `placeCalls === 0` assertion proves only that observing the external order does not itself submit an order; it does not test later strategy activity while the unowned order remains open.

**Strategy duplicate-order guard — strongly indicated risk:** `processMarketPriceTransition()` obtains `activeOrdersBefore` only from `state.registry.getActiveOrders()`. `evaluateLatestTransition()` passes only this registry list to `conservativeStrategyPolicy.evaluate()`, and calculates `allActiveOrders`, `committedQuote` and `committedBase` from the same registry. The policy's `hasActiveBuy`/`hasActiveSell` checks only its `activeOrders` input; with an empty registry and Portfolio, its initial BUY path can emit `INITIAL_BUY`. The account snapshot supplies exchange free balances (so locked funds are excluded), but if sufficient free quote remains the action can still be allocated. The submission `canSubmit` guard checks pause/readiness, market-price freshness and post-only crossing, not account-wide unowned open orders. Therefore, if a prior-process same-symbol order remains open but is unowned, a new same-symbol order may be submitted when the strategy emits an action and funds permit. This is strongly indicated by source, not reproduced: the existing startup test does not emit a market-price tick. The strategy unit tests prove that active orders suppress duplicate intents only when present in the supplied registry list.


This is explicit current behavior for external orders, not a reproduced duplicate-order incident. A prior-process Harvester order is indistinguishable from an external order when the new process starts with an empty registry.

## Graceful versus unexpected termination

- SIGINT and SIGTERM invoke the same graceful shutdown path.
- The shutdown handler performs owned-order reconciliation before and after the owned-BUY cancellation pass, drains user-data through final reconciliation, preserves open SELLs, writes the durable CLOSING balance audit and disconnects.
- Journal/EventBus close drains pending work and syncs. Process locks are released only after confirmed shutdown.
- SIGKILL, process crash and power loss bypass these handlers and cannot guarantee the graceful CLOSING path.
- A same-host lock is automatically reclaimed only when its recorded PID is demonstrably absent and PID/hostname/token still match on immediate re-read. Foreign-host, unreadable, permission-denied, or possibly-live locks fail closed and require operator verification.
- The existing #764/F-022 finding covers missing final CLOSING open-order evidence; this report does not duplicate it.
