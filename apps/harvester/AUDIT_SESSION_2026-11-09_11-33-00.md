**Scope:** evidence and documentation only; no implementation.

## Executive result

A process-restart persistence integration gap is confirmed in current `develop`: Harvester creates fresh in-memory trading projections and explicitly disables Journal replay. The shared Journal package has bounded read/replay capability, but Harvester startup does not invoke it or receive restored state.

The runtime consequences (missed offline fill accounting, duplicate new order, double accounting, or incorrect reservation decisions) are strongly indicated by the source paths but have not yet been reproduced in an end-to-end process-death/restart scenario. Do not describe them as confirmed incidents.

## What was inspected

### Startup composition and state ownership

- `apps/harvester/src/bootstrap/start-harvester.js` — initializes a fresh Portfolio, empty RecoveryLedger map, empty OrderRegistry and empty recovery/session collections; comment explicitly disables Journal replay.
- `apps/harvester/src/use-cases/create-portfolio-workflow.js` — creates Portfolio and RecoveryLedger projections in memory unless initial state is injected.
- `apps/harvester/src/domain/portfolio/portfolio.js`, `position.js`, and `src/domain/strategies/conservative/recovery-ledger.js` — position/accounting facts and fill IDs/fingerprints are owned by immutable in-memory objects.
- `apps/harvester/src/domain/orders/order-registry.js` — registry owns canonical orders; unknown exchange orders are deliberately not adopted.
- `apps/harvester/src/use-cases/conservative-trading-engine.js` — `reconcileOwnedOrders()` snapshots the existing registry; when it is empty, it returns `reconciled: 0` without querying canonical order or fill history.

### Journal and startup tests

- `packages/journal/README.md` — read/replay validates bounded complete history and invokes consumers sequentially; replay is at-least-once, not exactly-once.
- `apps/harvester/src/infrastructure/journal/prepare-optional-journal.js` — starts Journal and exposes ready/flush/close; no read/replay.
- `apps/harvester/src/index.js` — composes Journal and calls `startHarvester({ eventPublisher })`; no restored projection is passed.
- `apps/harvester/src/bootstrap/start-harvester.test.js`:
  - “starts from fresh in-memory state without replaying historical Journal records” injects malformed `journalRecoveryRecords`, instruments historical broker reads, asserts no history reads and `userDataReady === true`.
  - “journals pre-existing account-wide orders and allows trading startup without adopting or changing them” proves the unowned-order audit classification does not itself block runtime startup.
- These tests characterize current no-replay/unowned-order behavior. They are not crash/restart recovery tests.

### Graceful versus unexpected termination

- `apps/harvester/src/index.js` registers SIGINT and SIGTERM handlers.
- `apps/harvester/src/bootstrap/shutdown/create-shutdown-handler.js` performs owned-order reconciliation before and after the owned-BUY cancellation pass, keeps user-data intake active through final reconciliation, preserves open SELLs, and writes a durable CLOSING balance snapshot.
- The process closes Journal/EventBus and releases process locks only after confirmed shutdown.
- SIGKILL, process crash and power loss bypass signal handlers and cannot guarantee graceful CLOSING publication. A same-host lock is automatically reclaimed only when its recorded PID is demonstrably absent and PID/hostname/token still match on immediate re-read. Foreign-host, unreadable, permission-denied, or possibly-live locks fail closed and require operator verification.

## Broker history capability and completeness

The current `@coinzilla/brokers` contract exposes canonical `getFills({ symbol, orderId?, fromId?, startTime?, endTime?, limit? })`. A symbol-wide query can therefore discover trades without a local order ID. This is a useful building block for recovery, but current Harvester does not invoke it at startup.

The official [Binance Spot WebSocket API myTrades documentation](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/account) specifies:

- `fromId` is inclusive (trade ID greater than or equal to the cursor).
- Maximum page size is 1,000.
- Time-filtered queries are limited to a 24-hour interval.
- `fromId` cannot be combined with `startTime`/`endTime`.
- `orderId` cannot be combined with time filters, but can be combined with `fromId`.
- Without a filter, the endpoint returns the most recent trades up to the requested limit.

The broker package validates cursor IDs and rejects values outside JavaScript's safe-integer range rather than rounding int64 trade IDs. The official documentation reviewed does not establish a guaranteed retention horizon. Thus a complete scan needs durable per-symbol cursors, strict pagination/page-exhaustion validation, market-universe coverage, exact identifier handling and an explicit policy for unavailable historical data. The existence of the API does not prove all offline executions are retrievable.

## Documentation discrepancy

`apps/harvester/docs/JOURNAL_OPERATIONS.md` stated that Harvester reads all prior Journal sessions and blocks trading startup when previous trading events exist. Current source composition does not implement that gate. The operational documentation is corrected in this documentation change.

## F-028 — applied-fill Journal durability boundary

A second confirmed source-level gap compounds F-031:

- The Conservative engine applies a fill to accounting, then publishes `FILL_APPLIED`; the fill path does not call `eventPublisher.flush()`.
- `makeEventPublisher.publish()` is synchronous admission only. EventBus subscriber handlers are scheduled asynchronously and tracked as pending.
- Journal `record()` appends through a write queue and returns `durable: false`; Journal `flush()` waits for EventBus delivery and queued writes, then calls filesystem sync/fsync.
- The engine's only `eventPublisher.flush()` is the pre-side-effect intent barrier. It protects order placement/cancellation, not the applied-fill event.
- Graceful close drains pending work and syncs Journal. Abrupt termination/power loss has no equivalent guarantee.

**Classification:** confirmed lack of an immediate durability guarantee; no actual lost-fill incident reproduced. A crash in the publication/subscriber/write/sync window may leave the next process without a durable fill fact, which compounds the lack of startup replay in F-031. Journal is operational evidence, not a complete crash-consistent state ledger.

Existing tests verify fill-event publication and pre-side-effect intent durability, but no inspected Harvester test asserts durable flush immediately after applied fill. Future DDD/TDD work must define a crash-consistent ordering for fill fact persistence, accounting projection advancement and checkpoint advancement, with failure injection at each boundary.

## Existing projection and restoration seams — offline recovery helpers remain

The domain already exposes serializable value projections:

- `Portfolio.value` contains Position values, applied fill IDs and fingerprints.
- `Position.value` contains Market identity, base/free quantities, quote cash flow and spent amount.
- `RecoveryLedger.value` contains Market identity, buy cost, net sell proceeds and fill identities.
- `OrderRegistry.value` contains canonical order values.

Constructors still require typed domain objects (`Market`, `Quantity`, `Money`, `CanonicalOrder`). The repository supplies the use-case mapper `restoreHarvesterJournalState()` to hydrate those values from a validated `projectHarvesterJournalRecovery()` projection. `createPortfolioWorkflow()` accepts initial Portfolio and RecoveryLedger values, and `makeConservativeTradingEngine()` accepts an initial OrderRegistry, Journal fill identities and strategy/order-control sets. But current `startHarvester()` exposes no `journalRecoveryRecords` input and does not call the mapper; it constructs fresh state and passes those empty objects to the engine.

Therefore validated offline hydration and injection seams exist and have focused tests; current runtime composition wiring is missing. A complete search for any standalone restore helpers and serialization round-trip tests remains open.

## PREFLIGHT open-order classification versus readiness

`subscribeToUserData()` publishes the account-wide open-order audit, drains queued user-data events, and then sets `state.ready = true` when other user-data/accounting flags are safe. It does not gate readiness on the open-order audit's `BLOCKED` label. The existing startup test verifies that an unmatched open order is journaled as unowned while market subscriptions proceed and the runtime starts.

The test emits no market-price tick. Its `placeCalls === 0` assertion proves only that merely observing the order does not submit another order; it does not test a later strategy decision while that unowned order remains open. A later live execution event for the unowned order can trigger accounting safety, while a fill completed entirely during downtime is absent from the new user-data stream and the current open-order snapshot.

This is current explicit behavior for external orders, not a reproduced duplicate-order incident. A prior-process Harvester order is indistinguishable from an external order when the new process starts with an empty registry. This remains a central #654 acceptance requirement.

## F-029 — per-market strategy safety-pause and recovery-intent state is not restored on restart

The startup composition creates fresh `userDataState` with `accountingFailed: false`, `requiresReconciliation: !tradingEnabled` (false in trading-enabled mode), `ready: false`, and no recovery task. It also passes empty `pausedMarkets`, `durablePausedMarkets`, `recoveryManagedPausedMarkets`, replacement intents and cancellation IDs into the engine.

The engine stores pause state in in-memory Sets. `pause()` adds to `paused` and `durablePausedMarkets`, publishes `STRATEGY_PAUSED`, and does not flush. On restart, these per-market pause/recovery-intent sets reset; `subscribeToUserData()` can set readiness true after PREFLIGHT/queued-event checks, and `canTrade` reads that new readiness state.

**Classification:** confirmed process-local strategy-pause/recovery-intent state reset; post-restart unsafe resumption is strongly indicated but no actual duplicate order after a prior halt was reproduced. This is distinct from F-023's same-process latch and F-024/#773's safety-halt side effects. F-028 further limits the durability of the `STRATEGY_PAUSED` Journal event.

Future DDD/TDD work must persist pause scope/reason/generation and restore the halt before engine activation. Keep trading disabled until the original cause is authoritatively reconciled or explicitly acknowledged. Test graceful and abrupt restart after accounting failure, unknown order outcome, liveness failure and reconciliation conflict.

### Existing offline recovery implementation — retained, not wired into current startup

The repository still contains a substantial, tested recovery pipeline introduced by PR #606:

- `projectHarvesterJournalRecovery({ records })` validates Journal sessions, ordered lifecycle transitions, order intents/acknowledgements/cancellation outcomes, exact fills and duplicate identities, recovery cycles, pause state, PREFLIGHT/CLOSING account snapshots and open-order snapshots.
- `restoreHarvesterJournalState({ projection, marketMetadata })` rehydrates Portfolio, RecoveryLedger, OrderRegistry, paused/durablePaused/recovery-managed pause sets, replacement and trailing-reprice intents, cancellation identities, completed-cycle state and Journal fill identities. It deliberately restores unresolved orders as UNKNOWN/CANCELED and requires canonical exchange reconciliation before trading.
- `fetchAccountTradeHistory()` paginates `myTrades` by supplied Market list, beginning at the durable baseline and advancing with `fromId`. It cannot discover symbols that were not supplied; `marketUniverseComplete` is an explicit caller assertion.
- `auditRecoveredTradeHistory()` verifies exact Journal/exchange fill and commission parity, duplicate IDs and trade IDs, owned-order attribution, complete pages, and requires `marketUniverseComplete === true`.
- `auditRecoveredAccountState()` verifies the durable PREFLIGHT baseline, current balances, active open-order ownership/status/quantities and exact locked-asset reservations.

Focused offline tests exist in `project-harvester-journal-recovery.test.js`, `fetch-account-trade-history.test.js`, `audit-recovered-trade-history.test.js` and `audit-recovered-account-state.test.js`. These helpers are not called by the current `index.js`, `prepareOptionalJournal()` or `startHarvester()` composition.

**Historical PR #606 integration limitation:** the PR #606 caller passed `marketUniverseComplete: false` to `fetchAccountTradeHistory()`, while `auditRecoveredTradeHistory()` rejects unless that flag is true. Thus the prior trading-enabled integration deliberately failed closed when historical trading state required a complete account-wide history audit. The current Binance symbol catalog cannot prove the universe of historical symbols, including delisted markets. The current runtime later removed the recovery read/replay gate rather than solving this completeness problem; it now starts fresh and can proceed with unowned open orders. That bypass is not a safe equivalent to the previous fail-closed behavior.

**Order-ID recovery boundary:** durable submission intent preserves `clientOrderId`; broker `brokerOrderId` is captured by acknowledgement/cancellation/fill events or recovered by `reconcileOwnedOrders()` through `broker.getCanonicalOrder({ symbol, clientOrderId })` for restored orders without a broker ID. Tests cover lost acknowledgements, unresolved lookups, mismatched IDs and immutable-intent conflicts. If lookup fails, the order remains UNKNOWN and the account audit fails closed.
