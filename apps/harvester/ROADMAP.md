## Scenario Runner Linux sandbox implementation — 2026-11-27

PR #1913 now composes the RS simulation-only process adapter behind explicit `HARVESTER_SCENARIO_SANDBOX=linux-bubblewrap`. The launcher verifies trusted Bubblewrap/prlimit/shell/Node binaries and capabilities, then applies user/network/PID/IPC/UTS namespaces, seccomp network/child-process restrictions, a read-only runtime allowlist, a trusted Node installation directory bound read-only at its canonical host path, worker IPC preservation, RLIMIT_CPU, and a per-run delegated cgroup v2 (256 MiB hard memory, swap disabled, one CPU quota, 64 pids/threads). Seccomp allows Bubblewrap's initial `execve` to start Node while denying fork/vfork, non-thread clone, and execveat. The API remains fail-closed when the host lacks delegated cgroup controllers or any binary/capability check fails.

Runtime scenarios are eligible for simulation only; they remain PARTIAL and are not production-accepted. The primary functional developer acceptance path is local Windows with Dashboard + Harvester running together and simulated infrastructure. Linux Bubblewrap/cgroup adversarial E2E is optional platform-specific OS-hardening evidence, not a prerequisite for local scenario execution. Separate remaining product/security work includes trusted build-artifact provenance for exact replay, production operational-state persistence acceptance where required, and the independent RS lifecycle correction in issue #1842.

## Linux sandbox adversarial acceptance harness — 2026-11-27

A manual self-hosted workflow `.github/workflows/harvester-scenario-sandbox-e2e.yml` now runs the real Linux sandbox boundary test on a runner labeled `scenario-sandbox`. It verifies namespace separation, secret non-forwarding, read-only filesystem, network denial, child-process denial, and the per-run cgroup hard limits. It requires a trusted Linux runner with Bubblewrap/prlimit/Node root-owned and delegated cgroup v2 `memory`, `cpu`, and `pids` controllers. It is intentionally not run on the ordinary GitHub-hosted runner. Do not close the isolation acceptance gate until the manual workflow passes on the intended deployment class.

## Scenario Runner cgroup lifecycle follow-up — 2026-11-27

The cgroup setup leak and post-spawn cleanup-handle orphaning are fixed on `fix/harvester/scenario-runner-cgroup-cleanup`: argument construction is guarded; cgroup removal errors are surfaced; the process adapter withholds success until cleanup is confirmed; and cleanup handles are retained/retried even when launcher setup throws before returning a child. Spawn/registration is isolated from execution-promise construction to keep failure registration explicit. Regressions cover invalid worker path, seccomp/IPC setup failure after spawn, spawn failure before child creation, cleanup diagnostics, and retained-slot retry. Exact-head CI is pending. Trusted Linux sandbox E2E, trusted artifact provenance/replay and overall production acceptance remain separate gates.

## Replay provenance trust boundary and cgroup cleanup acceptance — 2026-11-27

[PR #1925](https://github.com/45s/coinzilla/pull/1925) rejects caller-supplied `replayProvenance.verified: true` even when the accompanying source, dependency, build, runtime and registry identity values are syntactically valid. Supplied identity remains diagnostic data only; exact replay stays blocked until a trusted build-artifact verifier is integrated into trusted runtime composition. The manual Linux E2E also asserts that the real per-run cgroup directory exists while the sandbox child is alive and is absent after the child exits. Hosted CI passing does not establish either trusted-runner execution or artifact attestation acceptance.

## Trusted build-artifact verification — still gated

The current repository has no trusted build-artifact producer, signing identity policy, attestation verifier, or deployed artifact handoff for the Harvester runtime. A hash generated by the running process, a caller-supplied `verified` flag, or an unsigned manifest cannot establish builder trust. Do not wire any of those into replay authorization. Exact replay remains fail-closed until a signed artifact from an explicitly trusted workflow is verified against the deployed runtime artifact and its source revision at the trusted host composition boundary. This requires an agreed immutable artifact handoff and a pinned workflow identity; it is not satisfied by the OS sandbox E2E workflow.

## Scenario Runner local acceptance environment — 2026-11-27

**Windows is the user's local development environment and the primary functional acceptance target.** Functional Scenario Runner checks are performed by starting the Dashboard client and Harvester server locally, executing scenarios through their local REST/WebSocket connection, and inspecting actual run status, assertions, results, trace and diagnostics. Scenario execution must use simulated broker/order and run-local state adapters; it must not touch live exchange accounts, credentials, or production persistence.

No Linux server, WSL2, self-hosted Linux runner, or purchased machine is required for this local functional workflow. The Bubblewrap/prlimit/cgroup E2E validates an additional Linux OS-isolation boundary only. Keep it separate from ordinary scenario functionality and do not treat its queued/pending status as a blocker to Windows development or functional acceptance.

If the current implementation cannot execute the simulation workflow on Windows, track and fix that as a Scenario Runner host-composition/platform-support gap. Do not turn the Linux-only hardening adapter into a user infrastructure requirement. Trusted artifact provenance remains a separate gate for exact replay authorization; it does not make Linux infrastructure necessary for ordinary scenario execution.

## Windows guarded simulation worker — 2026-11-27

The Harvester API now selects a dedicated Node child-process worker by default on Windows, without requiring a Linux sandbox environment variable. The worker uses a minimal environment and the existing Node module/network/filesystem guards. The host distinguishes this guarded simulation boundary from a verified OS sandbox: it supports local functional testing of repository-owned RS scenarios with simulated broker/order and run-local state, but it is not an OS security boundary, does not provide OS-enforced resource limits, and must not execute arbitrary user-supplied code. Linux Bubblewrap/prlimit/cgroup remains optional hardening. The Windows integration test is wired into a `windows-latest` CI job; acceptance is pending that job's result on the final PR head. Production acceptance remains PARTIAL and exact replay remains fail-closed pending trusted artifact verification.


The Linux sandbox acceptance workflow is manual-dispatch only (not triggered by pull requests). It is an optional OS-hardening check, not a required PR status or a prerequisite for Windows local functional acceptance. Do not wait for a self-hosted Linux runner to continue Scenario Runner feature development.
