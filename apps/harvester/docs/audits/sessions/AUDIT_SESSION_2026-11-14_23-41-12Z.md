## Executive result

The complete supplied Journal, structured application log, structured TRACE log and terminal capture establish one ZROUSDT BUY fill that was applied and reconciled to the supplied account snapshots, followed by an out-of-order/late-delivered Binance NEW execution report for the same already-FILLED order. The canonical order registry rejected the report because its cumulative executed quantity was zero after the registry had reached five. The event was classified as terminal ACCOUNTING_INTEGRITY / UNCLASSIFIED_ORDER_EVENT_TRANSITION, and the user-data handler latched accountingFailed, closed readiness and set EXECUTION_ACCOUNTING_FAILED.

**Confirmed defect (F-054):** the current stale-order predicate does not classify this FILLED → OPEN zero-cumulative report as stale when its timestamp is not earlier than the current order timestamp. The monotonic executed-quantity validator then throws “Canonical order executed quantity cannot move backwards”. The evidence establishes an order-event ordering/staleness defect; it does **not** establish that the BUY fill itself was lost.

The later TRADE report for the same trade was recognized as a duplicate. The Journal records one execution.fill_applied and nine execution.duplicate_fill events. The PREFLIGHT/CLOSING balance deltas independently agree with the net BUY quantity and quote debit:

- USDT: 8,496.51305077 → 8,489.62305077 = **−6.89 USDT**, equal to the recorded quote quantity.

The CLOSING account audit was correctly recorded INCOMPLETE and shutdown did not reach STOPPED. The evidence does not establish the exchange-side outcome of the attempted replacement, and it does not prove that this failure was caused by F-054.

The account-wide PREFLIGHT open-order audit also recorded five unowned orders and a BLOCKED audit classification. User-data readiness then became READY and the engine activated. ## 5. Confirmed finding F-054 — stale NEW report rejected after the order was FILLED

**Severity:** Critical — user-data accounting readiness and trading availability.  
**Verdict:** CONFIRMED.  
**Tracking:** [#1132](https://github.com/45s/coinzilla/issues/1132).

The application error is at harvester(3).log line 42 and trace(1).log line 72, timestamp 2026-11-14 23:41:25.359Z. The structured record contains:
- failureCategory: ACCOUNTING_INTEGRITY.
- failureStage: UNCLASSIFIED_ORDER_EVENT_TRANSITION.
- failureRetryable: false.
- eventType: executionReport, executionType: NEW.
- symbol: ZROUSDT, brokerOrderId: 873501, client ID h-0ecc1073c68b4683b3ccc3-1.
- Canonical incoming status OPEN (raw Binance orderStatus NEW), executed quantity zero.
- Registry matched both client and broker order IDs; the existing client-ID match was already FILLED.
- Error: “Canonical order executed quantity cannot move backwards”.

The preserved stack identifies:
1. src/domain/orders/order-registry.js:80 — monotonic executed-quantity validation throws.
2. OrderRegistry.applyUpdate at line 413.
3. prepareOrderEvent in src/use-cases/create-user-data-event-transition.js:40.
4. processUserDataEventTransition around line 584.
5. conservative-trading-engine.js:1266.

Source review on the same runtime commit confirms:
- isStaleOrderUpdate() classifies a report as stale when its timestamp is earlier (for a non-increasing executed quantity), when a CANCELED/EXPIRED order regresses to OPEN/PARTIALLY_FILLED, or when PARTIALLY_FILLED regresses to OPEN.
- It does not classify the observed FILLED → OPEN, zero-cumulative report as stale when its timestamp is not earlier.
- applyUpdate() runs that stale predicate before validateOrderUpdate(); the predicate returns false for this transition, and the monotonic quantity validator throws.

The user-data handler then sets ready=false, requiresReconciliation=true, accountingFailed=true, clears retryable recovery failure, sets safetyHaltRequired=true and persists a sticky safety blocker; it reports EXECUTION_ACCOUNTING_FAILED. The final shutdown summary later shows safetyHaltRequired=false after the shutdown/handler lifecycle progressed, while accountingFailed and requiresReconciliation remain true. The later TRADE report for trade 13588 is treated as a duplicate and does not clear the process-lifetime accounting-failure latch.

**Expected:** an out-of-order/late nonterminal report with no new execution must not regress an already terminal FILLED canonical order or convert an otherwise valid applied fill into a terminal accounting-integrity failure. The canonical order state and fill accounting must remain monotonic and exact-once.

**Actual:** the stale report is rejected as an accounting-integrity failure, readiness closes, and the process cannot recover through the normal retryable recovery path.

**Impact:** trading availability is halted after a fill that the Journal and account balances show was applied correctly. The error category/stage overstates the nature of this particular failure: the immediate throw is an order-transition monotonicity check, not a demonstrated loss or duplication of the fill.

**Containment:** the existing fail-closed behavior prevented further strategy readiness. Do not weaken it. Add a deterministic regression for FILLED followed by a zero-cumulative NEW/OPEN report with equal/newer event timestamp; verify the canonical order remains FILLED, no accounting delta is added, and the event is classified/handled as stale or otherwise safely ignored. Also cover older/equal/newer timestamps and partial-fill/terminal boundaries.

**Root cause confidence:** high for the order-registry stale-classification gap described above. No production code was changed and no regression test was run in this audit.
