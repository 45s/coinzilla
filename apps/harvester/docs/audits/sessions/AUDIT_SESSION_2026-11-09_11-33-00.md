**Order-state behavior in the retained PR #606 helper pipeline:**

| State at process exit / durable Journal facts | Offline restoration behavior | Canonical startup reconciliation requirement |
|---|---|---|
| `OPEN` / `PARTIALLY_FILLED` | `restoreHarvesterJournalState()` restores the order with its client ID, any known broker ID, cumulative executed quantity and fill identities, but conservatively sets status to `UNKNOWN`. | Resolve a missing broker ID through canonical `clientOrderId` lookup; compare canonical order history, current open orders and complete fill history; fail closed on mismatch or incomplete quantity/history. |

Unresolved intents keep the market paused and startup fails closed. |
| `CANCELED` with partial execution | Restored as CANCELED only with a broker ID; the helper re-adds a durable market pause for the partial-fill case. | Verify complete canonical fill history and retain the pause until recovery state is resolved. |

The current runtime does not execute this restoration/reconciliation matrix because it supplies an empty registry and never invokes the helper pipeline. The historical PR #606 path also retained the account-wide `marketUniverseComplete: false` blocker described above.

## Broker order identity recovery

- Durable `order.submission_requested` facts preserve `clientOrderId`.
- Broker `brokerOrderId` can be recorded by the submission acknowledgement, cancellation intent/failure, or applied-fill event.
- The engine's `reconcileOwnedOrders()` can also resolve a restored registry entry missing a broker ID through `broker.getCanonicalOrder({ symbol, clientOrderId })`, validate the returned symbol/client ID, and attach the canonical broker ID.
- Existing engine tests cover accepted orders after a lost submission acknowledgement, unresolved client-ID lookup, mismatched client IDs and immutable-intent conflicts.
- If the client-ID lookup cannot resolve the order, it remains UNKNOWN and reconciliation fails closed. The current runtime cannot use this path after restart because it does not restore the registry entry containing the client ID.

The current `@coinzilla/brokers` contract exposes canonical `getFills({ symbol, orderId?, fromId?, startTime?, endTime?, limit? })`. The offline `fetchAccountTradeHistory()` helper uses symbol-wide pagination for a supplied Market list, but current startup does not invoke it.

The official [Binance Spot WebSocket API myTrades documentation](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/account) specifies:

- `fromId` is inclusive.
- Maximum page size is 1,000.
- Time-filtered queries are limited to a 24-hour interval.
- `fromId` cannot be combined with `startTime`/`endTime`.
- `orderId` cannot be combined with time filters, but can be combined with `fromId`.
- Without a filter, the endpoint returns the most recent trades up to the requested limit.

The broker package rejects trade/fill cursor IDs outside JavaScript's safe-integer range rather than rounding int64 identifiers. The official documentation reviewed does not establish a guaranteed historical-retention horizon. The helper cannot prove complete account history while the full historical symbol universe is unknown.

**Strategy duplicate-order guard — strongly indicated risk:** `processMarketPriceTransition()` obtains `activeOrdersBefore` only from `state.registry.getActiveOrders()`. `evaluateLatestTransition()` passes only this registry list to `conservativeStrategyPolicy.evaluate()`, and calculates `allActiveOrders`, `committedQuote` and `committedBase` from the same registry. ## Graceful versus unexpected termination

- SIGINT and SIGTERM invoke the same graceful shutdown path.
- The shutdown handler performs owned-order reconciliation before and after the owned-BUY cancellation pass, drains user-data through final reconciliation, preserves open SELLs, writes the durable CLOSING balance audit and disconnects.
- Journal/EventBus close drains pending work and syncs. Process locks are released only after confirmed shutdown.
- SIGKILL, process crash and power loss bypass these handlers and cannot guarantee the graceful CLOSING path.
- A same-host lock is automatically reclaimed only when its recorded PID is demonstrably absent and PID/hostname/token still match on immediate re-read. Foreign-host, unreadable, permission-denied, or possibly-live locks fail closed and require operator verification.
- The existing #764/F-022 finding covers missing final CLOSING open-order evidence; this report does not duplicate it.

## Crash-boundary persistence trace — 2026-11-09

This section records source-level ordering from the current `develop`; it is not a process-crash reproduction.

### Verified persistence contract

- `makeEventPublisher.publish()` synchronously admits an event to EventBus. It does not await subscribers or claim durability.
- EventBus schedules each subscriber through a Promise task and tracks it in `pending`. `EventBus.flush()` waits for currently accepted delivery tasks to settle.
- Journal subscribes to all events. Its handler calls `record()`; `record()` serializes the event and queues `store.append()`. A successful append returns `written: true, durable: false`.
- `Journal.flush()` waits for EventBus delivery, then the Journal write queue, checks write errors, and calls the store's sync/fsync operation. Only that successful path returns `durable: true`.
- The trading event publisher's `flush()` delegates to the Journal flush (after process-start publication). The engine's durable-intent helper requires this barrier and rejects when it is absent, unsuccessful, or not explicitly durable.
- Submission intent is admitted and durably flushed in `onPendingOrder` before broker submission. If that barrier fails, the pending registry entry is removed, the market is paused, and broker submission is not attempted.
- The engine publishes `ORDER_SUBMITTED` after applying the broker acknowledgement to the in-memory registry, but does not immediately flush that acknowledgement event. The already-durable submission intent preserves clientOrderId for later canonical lookup.
- Applied-fill accounting advances the in-memory Portfolio/RecoveryLedger first, then publishes `FILL_APPLIED`; this path has no immediate durable flush. A successful Journal append alone is not fsync confirmation.
- `pause()` mutates process-local pause Sets and publishes `STRATEGY_PAUSED`, but does not immediately flush. These Sets are initialized from startup input; current bootstrap supplies empty collections.
- Cancellation uses a durable cancellation-intent barrier before the broker side effect. The later cancellation outcome event is published without an immediate dedicated fsync barrier; recovery must therefore resolve uncertain outcomes from canonical broker state.

### Failure-boundary matrix

| Boundary | Durable evidence before/after boundary | Restart disposition required |
|---|---|---|
| Before submission intent fsync | No broker submission is allowed by the current intent gate | Safe not-sent outcome; no order should exist |
| Intent fsync succeeds, crash before submit RPC | Durable clientOrderId intent exists; exchange outcome is not yet known from Journal | Query canonical order by clientOrderId; do not submit a second order until absence is authoritative |
| Submit RPC sent, acknowledgement lost | Durable intent exists; acknowledgement may be absent | Resolve by clientOrderId/order history/open orders/fills; UNKNOWN remains blocked |
| Acknowledgement applied in memory, ORDER_SUBMITTED not fsynced | Durable intent remains; acknowledgement event may be absent after crash | Reconstruct canonical broker state from clientOrderId; never infer not-submitted from missing ack event |
| Cancellation intent fsync succeeds, crash before/during cancel RPC | Durable cancel intent exists; cancellation result may be unknown | Query canonical order and complete fills; preserve UNKNOWN and pause until terminal outcome is authoritative |
| Cancel succeeds, outcome event not fsynced | Durable cancel intent exists; exchange may already be terminal | Reconcile canonical order/fills; do not repeat cancellation blindly |
| Fill received and accounting applied, before FILL_APPLIED publication | Portfolio/ledger update exists only in volatile memory; Journal may have no fill fact | Recover execution from complete broker trade history before rebuilding accounting |
| FILL_APPLIED published, subscriber/write pending | EventBus admission is not subscriber completion; Journal record may not yet exist | Treat Journal evidence as potentially absent; recover from broker history |
| Journal append completed, before fsync | Record reports durable:false; power loss may discard the unsynced append | Validate Journal, then reconcile every relevant broker execution; no exactly-once assumption |
| Strategy pause recorded only in Sets / event not fsynced | Pause can be lost with process memory and may be absent from Journal | Restore pause/recovery state before engine activation; readiness must remain closed until cause resolved |
| Graceful SIGINT/SIGTERM shutdown | Runtime shutdown drains reconciliation and Journal close/flush path when successful | Still require startup reconciliation; graceful close is not a substitute for proving offline activity |
| SIGKILL, crash, power loss | No signal handler, final CLOSING audit, or graceful Journal close is guaranteed | Treat all in-flight broker outcomes and unsynced facts as uncertain; startup must reconcile fail-closed |

### Required restart invariants and unresolved dependencies

1. A durable submission/cancellation intent is a recovery anchor, not proof of the final exchange state.
2. Missing acknowledgement/outcome events must never be interpreted as proof that the broker side effect did not occur.
3. A fill must not become a durable accounting checkpoint until its canonical identity, quantity, price, commission amount/asset, Portfolio/RecoveryLedger application and checkpoint advancement have a crash-consistent contract.
4. Journal replay is at-least-once. Projection restoration must be idempotent across a crash between application and checkpoint advancement.
5. The offline helper pipeline can restore Journal projections and reconcile supplied symbols, but market-universe completeness (including delisted symbols and external/manual activity) and broker-history retention are unresolved. Do not assert `marketUniverseComplete: true` without a defensible proof.
6. Current runtime does not call the read/replay/restore helper pipeline before activating the engine. Current open-order audit permits unowned orders without making that classification a readiness gate; strategy duplicate suppression sees only the in-memory registry.
7. The separate #764/F-022 missing CLOSING open-order snapshot remains a distinct evidence dependency.
